# Quest provisioning and charging procedure

Status: engineering procedure; physical station and spare qualification pending.
No Quest was connected during implementation. The Common procedures folder and
final ADR-005 audio choice were unavailable. This procedure records those gaps
instead of selecting study settings. The proposed engineering kiosk approach is
manual launch with focus-loss detection; it is not an Accepted ADR or device
management lock-down.

## Before provisioning

1. Assign each lab-owned unit a logical unit ID and its station or spare role.
   Staff confirm lab account ownership privately. Never use participant accounts
   or put account identifiers in these records.
2. Identify the protocol/apparatus version, approved audio route, station
   calibration and booking buffer. Resolve missing decisions with the apparatus
   owner before qualifying a unit. Read the current Common procedures when it
   becomes available and reconcile this procedure against it.
3. Obtain the approved APK and adjacent build manifest. The hosted CI guard
   currently reports missing Unity runner/license configuration; local validated
   builds are engineering artifacts, not a claimed CI release. Record which
   reviewed artifact is being installed. No runner installation or license upload
   is part of this procedure.
4. Use the already-installed Android SDK ADB. `list` prints counts, with serials
   suppressed. Obtain the intended serial locally, confirm it belongs to the
   labelled unit, and keep it in a private shell variable. Every device command
   below requires that explicit selection.

```powershell
python tools/quest_station.py list --adb $Adb
```

## Per-unit physical configuration

Perform these actions on every station unit and the spare. Record the exact UI
path and observed value on its current OS build; this tool does not change OS,
account, audio, boundary, networking or power settings.

1. Lab staff enable developer mode for the paired headset in the Meta Horizon
   mobile app and accept USB debugging on the selected headset. Follow Meta's
   current [developer-mode instructions](https://developers.meta.com/vr/documentation/android-apps/enable-developer-mode/).
2. Record the installed OS build before changing anything. Locate the supported
   update-deferral controls available on that build, record the method and any
   limitations, and document a manual pre-session update check. Do not claim a
   frozen OS if the device cannot enforce deferral. A required update creates a
   new reviewed apparatus version and requires recalibration before another cohort.
3. Suppress available notifications and participant-visible prompts. Review the
   actual headset view for residual system/account/setup prompts. Do not disable
   unknown system packages through ADB.
4. Configure and inspect the stationary boundary for the seated location. Check
   the seat, cable routing and physical clearance with the operator. The app's
   calibrated observer reference does not replace a safe physical boundary.
5. Attach the reviewed ADR-005 route. Record its physical connection, system
   volume reading and any automatic-volume control. Disable automatic changes
   only through supported controls after confirming the setting. Reboot, inspect
   the same value again, and compare all units. App gain is a separate control;
   this task does not choose participant gain or an audio route.
6. Record and apply the reviewed sleep setting (longest available was proposed).
   Record any unavailable control. Do not assume that a display timeout prevents
   runtime focus loss.
7. Label the unit and prepare its private `station.local.json` using #59's schema.
   Calibration, `protocol_version`, topology and source are explicit. Install the
   reviewed APK with the existing deployment script:

```powershell
./tools/deploy-quest.ps1 -Adb $Adb -Serial $DeviceSerial -Apk $Apk `
  -StationConfig $PrivateStationConfig -Python $Python `
  -Record .local/provisioning/deployment.local.json
python tools/quest_station.py inventory --adb $Adb --serial $DeviceSerial `
  --station-id station-01 --unit-id unit-01 --role station `
  --app-manifest "$Apk.build.json" `
  --output apparatus/stations/unit-01-baseline.local.csv
```

The inventory uses scoped read-only [ADB](https://developer.android.com/tools/adb)
and [dumpsys](https://developer.android.com/tools/dumpsys) queries. It pulls only
the selected app's single installed APK into an ignored sibling evidence folder
and hashes those bytes. Any mismatch is recorded and returns exit code 2. Version
labels alone cannot pass the check. It never overwrites an observation.

## Manual launch, focus and idle observation

1. From the headset library's sideloaded-app view, launch the installed experiment
   app. Confirm its private build/config log header, expected scene and seated
   reference. The app waits for tracked Device-origin state to remain stable for
   250 ms before initial restoration; this is an engineering startup interval,
   not a grace period for losing tracking during a session.
2. While using an engineering run, open the system menu, return, and separately
   exercise an actual pause/sleep and resume. Confirm private log events
   `application_focus_lost` or `application_paused`, `restore_pending: true`, and
   a neutral view. Unity can report focus and pause differently on Android; both
   callbacks are handled ([Unity documentation](https://docs.unity.com/en-us/engine/6000.3/script-reference/unityengine/monobehaviour/onapplicationpause)).
3. Returning focus must not silently resume the scene. Restore only through the
   operator/controller safe-boundary integration once the seated calibration pose
   is confirmed. If that control is not available in the installed build, end the
   engineering run and relaunch at a safe boundary; never accept a hidden auto-resume.
4. Perform the issue's proposed 30-minute idle observation on each unit, recording
   elapsed time and participant-visible headset output privately. Check for update
   prompts, notifications, boundary prompts and unintended volume/sleep changes.
   Any interruption is a failure to review, not a reason to delete the record.
   Simulator or callback tests do not establish this physical-device result.

## Battery observation and charging rota

1. Use the actual approved app workload, topology, audio route, brightness and
   accessories. Record these conditions privately. Start at the device's reported
   full charge and use the lab's normal battery-care procedure. Raw Android health
   codes are diagnostic status, not capacity measurements. The assessor requires
   Android's [reported discharging status](https://developer.android.com/reference/android/os/BatteryManager#BATTERY_STATUS_DISCHARGING).
2. Select the booking duration, additional buffer and sampling interval explicitly.
   The issue plans a longest booking of 75 minutes; no buffer or minimum starting
   percentage has been qualified. Observe long enough to cover the full selected
   duration. Do not extrapolate from a short discharge sample.
3. An unplugged endurance observation needs an already-approved noncharging ADB
   connection. This tool does not enable wireless debugging or change a network.
   If only charging USB/Link is available, preserve that powered observation as
   such; it cannot qualify unplugged endurance. Obtain an approved measurement
   route or leave this check pending.

```powershell
python tools/quest_station.py battery --adb $Adb --serial $DeviceSerial `
  --unit-id unit-01 --duration-seconds $ObservationSeconds `
  --interval-seconds $SamplingSeconds `
  --output apparatus/stations/unit-01-battery.local.csv
python tools/quest_station.py assess `
  --samples apparatus/stations/unit-01-battery.local.csv `
  --booking-minutes 75 --buffer-minutes $ApprovedBufferMinutes `
  --max-gap-seconds $ApprovedMaximumGapSeconds
```

Runs are bounded to eight hours; each command has a timeout. Interruptions retain
partial evidence and return nonzero. Assessment requires continuous reported
discharge, no external power, app process presence, a reported 100% start,
nonincreasing charge, the explicitly allowed sample gap, and enough observed
duration. Even a positive result requires operator review of the workload and
headset view. The tool supplies no charge threshold or remaining-time estimate.

4. Copy `charging-plan.example.json` to a private `*.local.json`. Enter measured
   evidence for each unit and spare, agreed buffer, start threshold and station
   assignments. If only full-charge duration has been tested, do not infer that
   a lower starting percentage is sufficient. Qualify any proposed lower threshold
   directly under the intended conditions.
5. Before each booking, record battery level and check the agreed policy. Rotate
   the spare in when a unit fails the policy, charge the outgoing unit, and verify
   the replacement has the same approved baseline. Record any planned powered
   operation explicitly; review the associated cable and safety arrangement.

## Pre-session and handoff

Capture a fresh private inventory and compare it with the signed baseline:

```powershell
python tools/quest_station.py inventory --adb $Adb --serial $DeviceSerial `
  --station-id station-01 --unit-id unit-01 --role station `
  --app-manifest "$Apk.build.json" `
  --output apparatus/stations/unit-01-current.local.csv
python tools/quest_station.py compare `
  --baseline apparatus/stations/unit-01-baseline.local.csv `
  --current apparatus/stations/unit-01-current.local.csv
```

A nonzero result stops provisioning approval. Reconcile identity changes, then
repeat the affected measurements under a new apparatus version. Independently
recheck manual audio, prompts, boundary and sleep settings; identity comparison
does not inspect them. Preserve the original baseline and raw observations.

The apparatus owner signs each completed unit record and charging plan privately.
Hand logical unit IDs and expected OS/app build contracts to #73's operator console
and #83's apparatus manifest. Train RAs on launch, fault handling, spare rotation
and escalation. No real unit can be marked provisioned from the public examples,
unit tests, local native builds or simulator observations alone.
