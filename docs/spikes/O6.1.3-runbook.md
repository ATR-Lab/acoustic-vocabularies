# O6.1.3 — audio onset calibration on the chosen route

Status: the offline analysis tool and the record schema are implemented and tested on
synthetic captures only. **No physical measurement has been made.** No station, route,
buffer or device setting is calibrated or qualified. ADR-005 still has no chosen route.
Unity loads a pinned record as described in
[study-audio.md](../unity/study-audio.md#onset-calibration-record-80). Until a
qualified record that matches the station is provisioned, the app keeps writing null
onset estimates and uncertainty, as described in
[audio-calibration.md](../unity/audio-calibration.md).

This runbook covers issue #80, Common procedures §2 check 5. It builds on the O5.1.6 spike
([runbook](O5.1.6-runbook.md), `spikes/O5.1.6/audio_onsets.py`). The O5.1.6 detector
counted pulses. This tool instead looks for the first onset of an arbitrary stored stimulus
after each logged request.

## What is computed

`tools/onset_calibration.py` (Python standard library plus the repository's `jsonschema`).
For each capture channel analysed:

1. **Clock map.** It fits `capture_s = intercept + slope * host_mono_ms / 1000` from
   independent sync anchors (at least 3 `fit` and 3 held-out `check`). The fit refuses
   extrapolation and a clock ratio outside 0.99–1.01. The rules are the same as O5.1.6:
   audio onsets are never used as anchors.
2. **Onset (detector `onset-threshold/1`).** For each play, the reference time is the
   logged `scheduled_onset_mono_ms` (see [Reference time](#reference-time)). The onset is the first sample that starts a run of
   `consecutive_samples` samples with `|x| >= threshold_fs * full_scale`. That run must
   start inside `[ref + search_start_ms, ref + search_end_ms]`.
   - The threshold is a fixed fraction of digital full scale and is frozen in the
     settings file. It is never tuned per play or after looking at results.
3. **Play status.** Each play gets one of these statuses:
   - `outside_capture`: its windows fall outside the WAV, for example after a
     truncation.
   - `clipped`: a rail sample appears from the start of the quiet window to the end of
     the search window.
   - `contaminated`: the quiet pre-window `[search_start - quiet_pre_ms, search_start)`
     already crosses the threshold.
   - `matched` or `missing`: a qualifying onset was found in the search window, or not.

   Windows of consecutive plays must not overlap; the tool refuses inputs where they do.
4. **Statistics.**
   - offset_i = onset_i - ref_i in host milliseconds.
   - `route_offset_ms` = median offset.
   - residual_i = offset_i - median.
   - `residual_abs_p95_ms` is the type-7 (linear interpolation) 95th percentile of
     |residual|. The record also stores the maximum |residual| and the SD of the
     offsets.
5. **Uncertainty and target (`onset-target/1`).**
   - `onset_uncertainty_ms` = `residual_abs_p95_ms` + held-out sync maximum error +
     the operator's `sync.external_bound_ms`.
   - `target.met` is true only when all of these hold:
     - at least 200 plays were requested;
     - every play is `matched`;
     - every profile × {atom, message} cell has a matched play;
     - `onset_uncertainty_ms <= 20`.

   The issue's criterion is p95 |residual| ≤ 20 ms. Adding the sync error, as ADR-005
   and O5.1.6 require, makes this check stricter, never looser. The bare residual p95 is
   recorded separately.
6. **Loopback diagnostic.** If `reference_channel` is set, each play also gets the
   measured-minus-reference onset delta. The median and the p95 deviation of these
   deltas are reported. They are diagnostics only and do not change the target decision.

## Inputs

All inputs are strict. Unknown fields, extra CSV columns, byte-order marks, duplicate
or non-increasing plays, non-finite or exponent-formatted numbers are all refused, and
so are compressed, 8-bit or float WAVs and a WAV whose rate differs from the declared
capture rate. A refused input produces no output.

- **Capture:** one uncompressed signed 16- or 24-bit PCM WAV with all channels on one
  interface clock. Its rate must equal `capture_sample_rate_hz`.
- **Events CSV:** the header must be exactly
  `play_id,stimulus_id,profile,stimulus_kind,audio_request_mono_ms,scheduled_onset_mono_ms`.
  - Times are plain decimal host-monotonic milliseconds, as exported from the app's
    playback log (`O5.4.1` / #64).
  - `profile` is `P1|P2|P3`; `stimulus_kind` is `atom|message`.
  - `scheduled_onset_mono_ms` must be filled on every row and must not precede the
    request. Rows must be in strictly increasing `scheduled_onset_mono_ms`.
  - `audio_request_mono_ms` is kept for audit only; it is never the reference.
- **Sync anchors CSV:** `host_mono_ms,capture_s,role`, with role `fit` or `check`. Use
  the same independent hardware procedure and evidence as in the O5.1.6 runbook.
- **Settings JSON:** see
  [schema](../../apparatus/schemas/audio-onset-calibration-settings.schema.json) and
  [synthetic example](../../apparatus/examples/audio-onset-calibration-settings.example.json).
  It records:
  - station, route and connection mode (`headset_speakers`, `wired_3_5mm_earphones` or
    `link_pc_headphones`; Bluetooth is not a candidate);
  - play mode, app build, output device and capture interface;
  - capture kind (`acoustic_coupler` or `electrical_loopback`);
  - app rate (always 48 kHz) and capture rate;
  - buffer frames and count, and the volume step out of its maximum;
  - whether the full scene was loaded;
  - the reference field, which must be `scheduled_onset_mono_ms`. The schemas refuse
    any other value;
  - `measured_at`, the sync bound and evidence, and the detector parameters with the
    source of the threshold.

## Reference time

Decision (maintainer, #80): the reference time for the measured route offset is
`scheduled_onset_mono_ms`, not `audio_request_mono_ms`.

- Unity's `AudioTiming.Schedule` takes a requested onset, subtracts `route_offset_ms`
  and schedules output at the result. That scheduled start is what the app logs as
  `scheduled_onset_mono_ms`.
- The measured offset is therefore onset − `scheduled_onset_mono_ms`. The app's
  `audio_onset_estimate_mono_ms` is `scheduled_onset_mono_ms` + `route_offset_ms`.
- The request time comes earlier than the scheduled start by a lead the app chooses
  (at least 100 ms plus clock uncertainty). Measuring from it would fold that lead into
  the offset.
- Because the offset is taken from the scheduled start itself, it does not depend on
  any offset the app applied while measuring. With the route unmeasured, as in the
  calibration host, the app schedules with zero offset and `scheduled_onset_mono_ms`
  equals the requested onset.
- Both schemas fix `reference_field` to `scheduled_onset_mono_ms`, and the tool refuses
  any other value. A `qualified` record must also use `play_mode: scheduled`, because a
  plain play has no scheduled onset to measure from.

## Procedure (operator, on hardware)

1. Confirm the ADR-005 route and fix its device settings. Record them in a settings file
   in an ignored `local-data/` directory. Set `evidence_kind` to `physical_measurement`.
2. Set up the measurement microphone in the ear coupler on the earphone, headset speaker or
   PC headphone, and a loopback tap where the route allows one. Use one capture interface
   for every channel. Disable AGC, noise suppression and automatic volume.
3. Verify the capture chain with a test click, for example with
   `python spikes/O5.1.6/audio_onsets.py click local-data/click.wav`. Record a separate
   noise-only capture with the scene running. Pick `threshold_fs` above that noise and well
   below stimulus peaks. Write how you chose it in `threshold_source`, then freeze it.
4. With the scene, panel and live mirroring running, play at least 200 stored 48 kHz mono
   stimuli through the scheduled playback path. Cover atoms (450–900 ms) and whole messages
   (1.1–2.0 s) from all three profiles. Space plays so that each stimulus has fully
   decayed before the next play's quiet window starts.
5. Export the events CSV and the independent sync anchors. Then run the analysis once for
   each capture channel, each into its own new directory:

   ```powershell
   python tools/onset_calibration.py analyze --capture local-data/capture.local.wav `
     --events local-data/events.local.csv --sync local-data/sync-anchors.local.csv `
     --settings local-data/settings.local.json `
     --output apparatus/calibration/<station>/<route>/<YYYYMMDD>-acoustic_coupler-scheduled
   python tools/onset_calibration.py check apparatus/calibration/<station>/<route>/<run>
   ```

   The tool writes `plays.csv`, `residual-histogram.csv` and
   `audio-onset-calibration.json`, always with `status: provisional`. It refuses an output
   directory that is not empty. Copy the analysed settings, events and sync files into the
   run directory. See [apparatus/calibration/README.md](../../apparatus/calibration/README.md)
   for how to store the capture WAV.
6. Investigate every play that is not `matched`. Never delete plays or retune the threshold
   to make a run pass. If `target.met` is false, investigate the buffer, scheduling and
   transport, repair them and rerun with a new directory. If p95 stays above 20 ms after
   repair, store a signed `response_time_qualification` with the record.
7. A reviewer can then mark a physical, acoustic, full-scene record as `qualified` by
   adding a `review` block. The schema enforces these conditions. The record path then
   goes into the manifest field `audio_onset_calibration_record`.
8. Bind the record in station configuration:
   - `audio.onset_calibration_record_sha256`: the SHA-256 of the record file;
   - `audio.route_offset_ms`: the record's `route_offset_ms`;
   - `audio.connection_mode` and `audio.output_device`: the same values as the record;
   - `audio.buffer_samples`: the record's `buffer_frames`.

   In the joined bootstrap, pin the same file as `audio_calibration`. Unity refuses a
   wrong pin. A provisional record, or a mismatch in station, route, connection mode,
   device, sample rate or DSP buffer, leaves the route unmeasured and logs the reason
   (see [study-audio.md](../unity/study-audio.md#onset-calibration-record-80)).
   - Any later change of route, device, buffer, rate, volume step or build invalidates
     the record. Unity checks all of these except the volume step and the build;
     those two are the operator's responsibility.

## Known limitations

- **Detector bias.** A threshold crossing lags the true start of a stimulus with a slow
  rise. A constant lag is absorbed into the offset; a lag that varies between stimuli
  shows up as larger residuals.
  - Coupler and microphone response and channel skew are not corrected. Investigate
    them with control pulses, as in O5.1.6.
- **Pairing.** The search window must contain the true onset. A spurious crossing inside
  the window gives an early onset; check `plays.csv` against the histogram for outliers.
- **Reference choice.** The issue text describes the estimate as request plus offset.
  The maintainer decision replaces this with `scheduled_onset_mono_ms` plus offset, to
  match `AudioTiming.Schedule` (see [Reference time](#reference-time)). Records with
  any other reference are refused.
- **Synthetic tests.** `tests/test_onset_calibration.py` uses generated square-wave bursts
  with injected offsets, integer-sample jitter, dropouts, clipping, pre-window noise,
  truncation, silence and wrong rates. These checks show that the analysis behaves as
  specified. They say nothing about any device or route.
