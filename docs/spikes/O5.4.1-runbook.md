# O5.4.1 audio validation

Use the pinned Unity editor and already approved dependencies. Keep participant
packages, reserved WAVs, calibration reports, coded IDs, raw logs and recordings
outside Git and Assets. Never provision example hashes as measured route evidence.

## Software checks

From the repository root in PowerShell:

```powershell
./tools/build-unity.ps1 -Unity $UnityEditor -Target Test -Scene Calibration -ProtocolVersion engineering-pending-review -BuildId audio-editmode-run
./tools/build-unity.ps1 -Unity $UnityEditor -Target TestPlayMode -Scene Calibration -ProtocolVersion engineering-pending-review -BuildId audio-playmode-run
./tools/build-unity.ps1 -Unity $UnityEditor -Target Windows -Scene Calibration -ProtocolVersion engineering-pending-review -BuildId audio-windows-run
./tools/build-unity.ps1 -Unity $UnityEditor -Target Android -Scene Calibration -ProtocolVersion engineering-pending-review -BuildId audio-android-run -TemporaryDirectory $ShortPrivateTemp -GradleCache $ShortPrivateGradleCache
```

Use fresh build IDs. The wrapper rejects dirty source and verifies every produced
file against the manifest. A short Gradle cache is needed for Ninja's Windows
path limit; no system long-path setting is changed. Preserve failed logs.

Run `AcousticVocab.StudyAudio.PlayModeTests` through Unity's PlayMode runner with
an actual 48 kHz output device. This suite schedules 100 silent stored-PCM clips
and requires callback-observed completion, separately from acoustic delivery.
It also injects effect, changed-clip and component-disable faults. Edit tests
inject missing/gapped/overlapping callbacks, invalid clock/calibration reports,
changed WAV bytes and torn gain histories, and reproduce all 18 trained phrases.
The tests do not authorize loading a participant package into a public CI job.

## Calibration UI

Follow [the calibration configuration guide](../unity/audio-calibration.md) to
provision the three exact #14 examples and a synthetic engineering coded ID.
Keep a copy of preexisting station files before testing. Choose the actual stored
profile order; never invent a participant allocation. Record build/config hashes,
headset/runtime, route and all private log hashes in the results template.

Verify quiet initial gain, a logged comfort adjustment while idle, six complete
software plays in the three-profile order, a two-second requested gap within each
pair, answers enabled only after both plays, and gain restored on a second launch.
Verify focus loss, stop and interrupted playback latch and require explicit
operator recovery. Do not relax focus guards to accommodate an automation tool.
Meta XR Simulator can check rendering and reported faults; it cannot certify
physical comfort, controls, legibility or acoustic onset. Keep its runtime only
if the owner requests it; otherwise restore the prior runtime with the owner's
Windows permissions.

## Needs operator run

On the chosen Quest/audio route, collect 100 scheduled plays with request time,
onset estimate, uncertainty, offset and callback completion, plus loopback and
earphone-microphone measurements from #80. Inject a controlled underrun and verify
the correct fault and no automatic replay. Measure preload/headroom on the device,
check identical nonspatial output in both ears, and record the calibration screen.
Review physical comfort and legibility with the operator. Preserve the actual raw
CSV, audio traces, device logs and hashes. No participant/pilot use before the
required approvals. The template deliberately contains no fabricated measurements.
