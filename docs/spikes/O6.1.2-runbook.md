# O6.1.2 view-capture leakage preparation

Status: offline verifier, protected Unity capture driver and manifest assembler
implemented and tested on synthetic inputs only. **No capture run has been
performed** on a station, the Meta XR Simulator or a headset. Complete capture,
the real protected trial boundary and the independent code-path review
([draft checklist](../tests/view-leakage-code-path-review.md)) remain pending.
No G3 acceptance, participant admission or qualified source selection follows
from these tools. The external methodology folder remains unavailable, so these
are explicit engineering proposals based on issue #79.

## Freeze before any capture

Copy `apparatus/spikes/O6.1.2/capture-plan.example.json` and the exact registered
neutral snapshot into a fresh operator-controlled private directory. Keep the
plan's snapshot reference relative to that directory. Replace the zero build and
panel hashes with independent pins for the actual binary and fixed response-panel
state. Confirm the actual source selected by the G2 decision; the example's live
setting does not make that decision. Provision the actual station identity.

The current profile requires exactly five distinct named views: center, yaw left,
yaw right, pitch up and pitch down. The example proposes one fixed Unity-world
camera position, yaw ±15 degrees and pitch ±10 degrees. These are **not** measured
headset poses or approved methodology constants. Establish the actual observer
reference and freeze all five absolute Unity left-handed, Y-up poses before the
run. Quaternions use XYZW. Isaac state retains its separate USD Z-up convention.
Do not change camera placement or tolerance after inspecting differences.

The current pixel tolerance is exactly zero on every decoded RGB/RGBA channel,
including alpha. Relaxing it requires a separately reviewed profile/code change.
The plan also fixes dimensions, a basic nonblank-color screen, maximum local
state-arrival age, and head matching bounds (at most 1 mm / 0.5 degrees). Head
poses must be distinct by more than the matching bounds. Registered-state bounds
cannot exceed #53: joints/orientation 0.5 degrees, positions 1 mm, velocities
1e-5 and workcell material/light scalars 1e-7. Discrete state, visibility, registry,
joint order, panel, text and routing remain exact. A dimension product over
4,194,304 pixels is refused to bound one 32-image pose group.

Independently record the plan's raw SHA-256 **before** capture. The verifier checks
the pin and declared capture ordering; it cannot prove predeclaration custody or
authenticate the operator. Use the already installed Python runtime:

```text
python tools/view_leakage.py --plan <absolute-private-plan.json> --plan-sha256 <raw-plan-pin> --validate-plan
```

## Capture contract

The protected capture driver is `unity/Assets/ExperimentApp/Runtime/ViewCapture/`
(`ViewCaptureDriver`, ports in `UnityCapturePorts.cs`, native entry
`ViewCaptureHost`). Its assembly compiles only with `UNITY_EDITOR` or
`AV_SIMULATION_TEST`, so ordinary players do not contain it. At runtime it also
requires the compiled capability, a loaded pinned `SIMULATION_TEST` capability,
and a #55 private control session whose `test` mode is acknowledged; otherwise
it refuses before creating output. For each plan pose (plan order) and each of
the 32 legal pairs (verifier order) it:

1. hands the pair to the trial boundary port (the only consumer of the pair);
2. requests a fresh `reset` and waits, bounded by the step timeout, for that
   exact accepted `RESET_COMPLETE` test-mode reply plus a later current health
   probe (`PrivateModeResetClient.ResetAcknowledged`); the raw wire reply is
   kept and its fields are rechecked;
3. places the participant camera at the plan pose (`desktop_engineering`) or
   waits for the tracked head to reach it (`headset`), then reads it back after
   the configured settle frames — a placed camera that reads back outside the
   plan bounds is refused immediately;
4. waits the configured pre-cue frames, then requires a post-reset neutral
   state sample, the same reset still current, the panel pin, no console or
   diagnostic overlay, and the pose again;
5. renders the participant camera offscreen at the plan dimensions (RGB24 PNG),
   re-reads the pose (movement during capture refuses), then marks the cue
   request.

The first refusal stops the run: no reset, pose or capture is retried and no
capture is skipped. Every file is created new, flushed and re-read against its
SHA-256; nothing is replaced. A row is appended to `rows.jsonl` only after all
of its files are durable. `status.json` records `complete` and the first fault
code; a failed run keeps every earlier file.

Current limitations, all of which keep the result at `HOLD`:

- The native host's trial boundary is `DriverOnlyTrialBoundary`: it keeps the
  pair in the driver and schedules no cue audio. It does **not** load a trial
  through the session engine. A capture with it does not meet the "load the
  trial through the real protected boundary" requirement above; a reviewed
  session-engine boundary is still required.
- The image is an offscreen mono render of the participant camera, not the
  compositor/eye-buffer output and not an OS or simulator overlay capture.
- Snapshot source: the per-capture `state` is the pinned neutral snapshot state
  after the host's own reset/neutral checks, not an Isaac readback. Live source:
  Unity records only the applied public projection and frame identity; the
  complete #53 state is joined offline from the Isaac observation journal by
  `tools/view_capture_assemble.py` using the rendered frame's left-bracket
  sequence, its reset lineage and a tolerance check of the applied projection.

The existing `RenderedAcknowledgmentFramesMatchAllOutcomes` seam in
`unity/Assets/ExperimentApp/Tests/PlayMode/Assessment/AssessmentBlockTests.cs`
remains a separate eight-outcome acknowledgment observation. Do not relabel its
images as the required matrix.

The driver must run a nonstudy capture for every legal command and every pose
(32 × 5 = 160), with the response panel held constant and no scheduled study
audio. Load the trial through the real protected boundary, request a fresh reset,
observe its exact accepted test-mode acknowledgment, set/read back the fixed head
pose, then capture immediately before the real software cue request. All capture
timestamps below are decimal nanosecond strings from the **same client monotonic
clock**. Do not compare remote Isaac timestamps directly with them. Arrival age
does not qualify source-clock freshness or acoustic onset.

The private capture manifest has exactly these fields:

- `version: 1`, `scope: "actual_nonstudy_capture"`, `plan_sha256`, `station_id`,
  `clock_id` (32 lowercase hex), `plan_seen_ns`, `captures`, `command_log`.
- Each capture has `capture_id` (unique 32-hex), `pose_id`, `action`, `target`,
  `head_pose` (`position_m`, `rotation_xyzw`), `reset_received_ns`, `captured_ns`,
  `cue_requested_ns`, `state_sample_ns`, `reset_reply`, `image`, `state`, `audio`,
  `view`. The last five are `{ "path": "relative-name", "sha256": "raw-file-pin" }`.
- `reset_reply` is the exact native #55 private reply, with a fresh request ID,
  accepted successful reset or mode change, mode test, no fault/pause/demo and
  exposure-ready health. It is evidence to inspect, never a newly issued grant.
- `image` is the actual noninterlaced 8-bit RGB/RGBA PNG. Images and full state
  captures have distinct file paths per capture; an existing neutral file cannot
  be substituted for a missing sample. No resizing, normalization or image
  editing occurs. Palette, animation, interlace, malformed chunks, excess decoded
  bytes and changed CRCs are refused. Color interpretation metadata must match.
- `state` is the complete #53 readback shape: `robot`, `objects`, `environment`,
  `frames`. It must match the pinned snapshot's complete registries. Capture both
  the Isaac readback and the visibly applied state in the native driver; this
  verifier consumes the former, and their alignment still needs review.
- `audio` has exactly `spatial_blend`, `pan_stereo`, `doppler_level`, `spread`
  (all zero), `volume`, `pitch` (one), `mute` (false), `enabled` (true), `loop`
  (false), `output_mixer_group`, `route_id`, `source_count` (one), `effects` ([]).
  Read real settings; identical metadata cannot substitute for acoustic checks.
- `view` has exactly `panel_state_sha256`, `visible_text` (ordered strings),
  `renderer_inventory_sha256`, `console_visible` (false), `diagnostics_visible`
  (false). Inventory the actual visible renderers/text; declarations alone do not
  prove an overlay or hidden-answer object was omitted from capture.
- `command_log` references the actual #55 v0.3.1 private command JSONL. It must
  contain exactly one nonduplicate rejected demo request for every legal pair,
  with `PROTECTED_TARGET_COMMAND`, matching raw command/arguments/request ID,
  test mode, station and control session. The capture resets and lock probes must
  share that session. Preserve other raw evidence separately rather than editing
  a log to fit this diagnostic window.

Legal pairs are ADD_ONE, REMOVE_ONE, FLIP_CARD, ALIGN_ARROW × tray_A–D, and SCAN,
TAG, CLOSE, QUARANTINE × container_E–H. These are the existing public command API
names. Private capture records contain their intended pair; never publish those
records as participant output or use them as renderer input.

## Local native procedure (Windows, Meta XR Simulator)

This is the exact procedure for one engineering capture run. It has not been
executed; record every deviation and retain failed attempts.

1. **Build.** From a clean commit, with PowerShell 7:
   ```text
   pwsh tools/build-unity.ps1 -Unity "<Unity 6000.6.0f1>\Editor\Unity.exe" -Target Windows -Scene ViewCapture -ProtocolVersion simulation-test-v1 -BuildId <fresh-id> -G1Description <reviewed g1_description.json>
   ```
   The `ViewCapture` scene holds the foundation, workcell, state source, fixed
   response panel, the inert shared audio owner and `ViewCaptureHost`; it has no
   session engine or schedule. The builder always adds `AV_SIMULATION_TEST`.
   Use the raw SHA-256 of `unity/Builds/<fresh-id>/Windows/experiment.exe.build.json`
   (which pins every player file and the commit) as the plan's `build_sha256`.
2. **Provision** the player's `persistentDataPath`
   (`%USERPROFILE%\AppData\LocalLow\AcousticVocab\Acoustic Vocabulary Experiment\`):
   `station.local.json` (topology `pcvr_link`, the plan's `station_id`, and
   `robot_state_source` equal to the plan's `source_kind`),
   `state-source.local.json`, its neutral snapshot (the plan's pinned snapshot
   bytes) and `response-panel.local.json`. Preserve and later restore any files
   already there.
3. **Capability.** Prepare a create-new `simulation-test.local.json` with the
   exact `SIMULATION_TEST` fields in [native simulated visits](../unity/native-simulation-tests.md)
   for this build ID and protocol. Its `output_directory` must be an existing,
   fresh private directory with a `simulation-test-...` segment below `.local`,
   `private` or `local-data`. Record its raw SHA-256 independently.
4. **Panel pin.** The fixed panel state is the closed, unopened panel. Its pin is
   the SHA-256 of the canonical descriptor (sorted keys, compact separators,
   ASCII, terminal newline) built from the raw SHA-256 of the provisioned
   `response-panel.local.json`:
   ```text
   python -c "import hashlib,json,sys;d={'version':1,'kind':'view_capture_panel_state','configuration_sha256':sys.argv[1],'request_open':False};print(hashlib.sha256((json.dumps(d,sort_keys=True,separators=(',',':'))+'\n').encode()).hexdigest())" <panel-config-sha256>
   ```
5. **Plan.** Freeze the plan as described above, with `capture_surface`
   `desktop_engineering` for the simulator (the driver places the camera and
   disables its tracked-pose driver) or `headset` (the driver only reads back the
   tracked head; the operator must bring the simulated/real head to each pose
   within the step timeout, once per 32 consecutive captures). Validate it with
   `--validate-plan` and record its raw SHA-256 before any capture.
6. **Isaac.** Reserve a fresh private control session and station, then start
   the isolated joined service exactly as in
   [the observation journal](../isaac/view-state-observations.md) and the
   loopback relays used for [native simulator attempts](../tests/native-simulator-attempts.md).
   For a live source add the five `--view-observation-*` options with this plan
   pin. Capacity: the journal is bounded to 4096 combined rows, so the whole live
   run must stay within roughly (4096 − 160) publications; keep settle/pre-cue
   frames small and expect an incomplete journal (and a refused assembly) if the
   run is slow. For the `snapshot` source the command service is still required
   for resets and the lock probe; Unity renders the pinned snapshot.
7. **Simulator.** Select the Meta XR Simulator OpenXR runtime as in the
   [O5.3.4 simulator checks](O5.3.4-runbook.md), recording and later restoring the
   previous runtime. Keep the player window focused for the whole run; focus loss
   faults the foundation and the capture stops with a recorded fault.
8. **Launch** the player:
   ```text
   experiment.exe -viewCapturePlan <private plan.json> -viewCapturePlanSha256 <raw pin>
     -simulationTestConfig <private simulation-test.local.json> -simulationTestConfigSha256 <raw pin>
     -viewCaptureControlEndpoint ws://127.0.0.1:<port>/commands -viewCaptureControlSession <32-hex session>
     -viewCapturePoseSettleFrames 2 -viewCapturePreCueFrames 2 -viewCaptureStepTimeoutMs 3000
     -viewCaptureRunName view-capture-<fresh-id> -viewCaptureQuitOnComplete -logFile <fresh private native.log>
   ```
   All capture arguments are required; without `-viewCapturePlan` the host stays
   idle. The settle/pre-cue/timeout values above are examples; record the
   values used (they are also written to `run.json`). The player requests `test`
   mode, then runs all 160 captures. Output: `<output_directory>/<run name>/`
   (`run.json`, `rows.jsonl`, per-capture `cNNN-*` files, `status.json`) and the
   durable private control journal `<output_directory>/<run name>-control.jsonl`.
   `VIEW_CAPTURE_STATUS` lines in the player log report progress; exit code 0
   means `status.json` says `complete:true`, 1 means a recorded fault.
   Immediately record the raw SHA-256 of `status.json`. The unchanged 250 ms
   private-health freshness bound applies at the reset acknowledgment and again
   at capture; earlier native attempts exceeded it
   ([native simulated visits](../unity/native-simulation-tests.md)), and such a
   miss stops the run with `RESET_ACK_TIMEOUT` or `RESET_NOT_CURRENT_AT_CAPTURE`
   rather than being retried.
9. **Lock probe and source finalization.** After the player exits (its control
   client is disposed), explicitly release ownership and run the lock probe
   against the same source still in test mode, then finalize the source and
   join the probe, exactly as in [the observation journal](../isaac/view-state-observations.md).
   Use the finalized `commands.jsonl` (live: the copy pinned by the observation
   manifest).
10. **Assemble** the verifier manifest in the untouched run directory:
    ```text
    python tools/view_capture_assemble.py --plan <plan.json> --plan-sha256 <raw pin> --run <run directory> --status-sha256 <status pin> --commands <finalized commands.jsonl> --commands-sha256 <pin> [--observations <observation manifest.json> --observations-sha256 <raw pin>]
    ```
    `--observations` is required for `live` and refused for `snapshot`. The tool
    refuses an incomplete run, a lock-probe session other than the capture
    session, a missing/unbound observation and any existing output. It writes
    `captures.json` (and, for live, `cNNN-state.json`) create-new and prints the
    manifest pin. After a refusal, retry only in a fresh copy of the original
    run files; never edit or delete retained outputs.

## Verify and investigate

Use the assembled `captures.json` and the pin printed by the assembler.

```text
python tools/view_leakage.py --plan <absolute-private-plan.json> --plan-sha256 <raw-plan-pin> --captures <absolute-private-captures.json> --captures-sha256 <raw-manifest-pin> --output <fresh-absolute-private-report.json> --comparison-csv <fresh-absolute-private-comparisons.csv>
```

The output must be below a user private directory (`.local`, `private` or
`local-data`). Reads are bounded and pinned; linked/reparse/hardlinked, remote,
traversing or changed files are refused. No file is replaced. Exit 2 means
invalid/missing evidence; exit 1 means a complete comparison found differences;
exit 0 means this bounded offline screen passed. All results remain `HOLD`,
`g3_signed: false`, `participant_ready: false`.

The report and optional comparison CSV enumerate all 496 command pairs at each
of five poses (2,480 total). If a later export fails, retain the partial output
and retry with fresh paths; a partial export is not a successful run.
It checks each state against neutral **and** against every other command, avoiding
a two-sided tolerance error. It compares every decoded channel. A failure records
the first above-bound pixel, not an invented maximum or changed-pixel count.
Investigate every image, state, text, renderer inventory or routing difference;
retain the failed run and start a fresh pinned plan/run after any correction.

Archive the plan, independent pre-run pin, manifest, frames, state/settings files,
private command log, report and reviewer notes in restricted storage. A second
reviewer must audit hidden-tuple readers in the engine, state mirror, command
lock, demos, audio, logging and console. Review dynamic camera visibility, robot
asset appearance outside the registered workcell material/light accessor, and
the real capture boundary. No screenshot similarity substitutes for that review.
Optional response-closure capture must cover right/wrong/timeout with fixed
timing; the prior eight-acknowledgment result is only a separate bounded software
observation. Complete headset/live-or-selected-snapshot capture, natural head
movement, acoustic route confirmation and independent sign-off remain pending.
