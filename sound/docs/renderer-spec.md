# Renderer specification

Spec version: **0.1.0** (renderer version `0.1.0`). Status: **pilot default; every
decision below freezes at G4** (renderer version `1.0.0`). Any change that alters
rendered bytes for any valid recipe requires a renderer version bump and new
golden hashes in the same pull request.

This document is the implementation manifest that Study A protocol §3.2 requires:
exact envelope, normalization target, limiter policy, rounding to samples and
renderer hash. It answers every question needed to re-implement the renderer bit
for bit. The machine-readable recipe contract is
[`sound/schema/recipe.schema.json`](../schema/recipe.schema.json).

## 1. Fixed inputs (protocol)

These are not choices. They come from Study A protocol §3.2 and the protocol
constants, and they apply to Study A and Study B.

| Item | Value |
| --- | --- |
| Motif | 3 tone events, gap after events 1 and 2 |
| `total_ms` (T) | 450, 600, 750 or 900 |
| `pitches` (p) | 3 integers, −6 to +6 semitones |
| `rhythm_weights` (w) | 3 integers, 1 to 4 |
| `gaps_ms` (g) | 2 values, each 20, 40 or 60 |
| `amplitudes` (a) | 3 values, each 0.6, 0.8 or 1.0 |
| Event frequency | `f_j = f0 * 2^(p_j / 12)` |
| Event duration | `(T - g1 - g2) * w_j / sum(w)` |
| Profiles | P1, P2, P3 with `f0` = 300, 450, 675 Hz |
| Partials | 1x, 2x, 3x with weights 1, 0.15, 0.05 |
| Envelope | 10 ms attack, 30 ms release |
| Admissibility | reject (never repair) any event shorter than 60 ms |
| Output | mono, 48 kHz WAV; global playback gain is not a generated feature |

At 48 kHz one millisecond is exactly 48 samples, so every `total_ms` and gap is a
whole number of samples. Only event durations need rounding. The highest partial
is `3 * 675 * 2^(6/12)` ≈ 2,864 Hz, far below the 24 kHz Nyquist limit, so no
anti-aliasing step exists.

## 3. Decisions

Every decision in this section is a **pilot default; freezes at G4**.

### D1. Sample rounding

All timing uses integer arithmetic on samples.

```
D  = (T - g1 - g2) * 48            # samples shared by the three events
W  = w1 + w2 + w3
n1 = floor((2 * D * w1 + W) / (2 * W))   # round half up of D * w1 / W
n2 = floor((2 * D * w2 + W) / (2 * W))
n3 = D - n1 - n2                     # event 3 takes the remainder
```

Layout: event 1 starts at sample 0, then `g1 * 48` zero samples, event 2,
`g2 * 48` zero samples, event 3. The motif length is exactly `T * 48` samples.

The 60 ms rule is checked on samples: an event is admissible when
`n_j >= 2,880`. The table
[`data/shortest-event-samples.csv`](data/shortest-event-samples.csv) (generated by
[`../tools/shortest_events.py`](../tools/shortest_events.py)) lists `n1`, `n2`,
`n3` for all 4 x 64 x 9 = 2,304 timing structures:

| `total_ms` | Admissible structures |
| --- | --- |
| 450 | 387 / 576 |
| 600 | 558 / 576 |
| 750 | 576 / 576 |
| 900 | 576 / 576 |
| All | 2,097 / 2,304 |

The shortest admissible event is exactly 2,880 samples (for example T=600, weights
1/4/4, gaps 20/40). The longest rejected event is 2,812 samples (T=450, weights
3/3/1, gaps 20/20). The sample rule and the exact-duration rule
(`D * w_j / W >= 2,880`) agree on all 2,304 structures, so rounding never changes
admissibility.

Rationale: the motif length is exact, all three implementations of a rule (spec,
renderer, validator) use the same integers, and boundary cases cannot drift with
floating-point rounding.

### D2. Envelope shape

Each event has its own envelope, in Q15 fixed point (32,768 = 1.0). For an event of
`n` samples and event-local index `i` (0 to `n - 1`):

```
A = 480                   # 10 ms attack
R = 1440                  # 30 ms release
EA[k] = round_half_up(32768 * (1 - cos(pi * k / A)) / 2),  k = 0..A
ER[k] = round_half_up(32768 * (1 - cos(pi * k / R)) / 2),  k = 0..R
env(i) = min(EA[min(i, A)], ER[min(n - 1 - i, R)])
```

So `env(0) = 0`, the attack reaches 1.0 at `i = 480`, the release starts at
`i = n - 1 - 1440` and reaches 0 at the last sample `i = n - 1`. The curve is a
raised cosine. Admissible events (at least 2,880 samples) always have a flat
middle section, because attack plus release is 1,921 samples. The `min` rule only
matters for the shorter events that the renderer still renders for diagnosis.

Rationale: a raised cosine has no slope discontinuity at either end, which
avoids onset and offset clicks. A per-event envelope keeps each event's onset
sharp and its duration exact.

### D3. Harmonic phase

At each event onset, every partial starts at sine phase 0. Phase restarts at the
start of every event. Each partial is a sine, not a cosine.

Rationale: the first sample of every event is exactly 0, which matches the
envelope's zero start and keeps the waveform a pure function of the recipe.

### D4. Arithmetic and determinism

The sample path uses only integers. It uses no floating-point numbers and no
platform math library, so output cannot depend on the CPU, the OS or the libm
version.

- **Sine table.** `S[i] = round_half_up(2^30 * sin(2 * pi * i / 65536))`,
  `i = 0..65535`, signed 32-bit, exactly odd-symmetric (quarter wave mirrored).
- **Phase increments.** For each profile, pitch `p` (−6 to +6) and harmonic
  `h` (1 to 3): `INC[profile][p][h] = round_half_up(h * f0 * 2^(p/12) * 2^32 / 48000)`.
  There are 117 unsigned 32-bit values.
- **Envelope tables.** `EA` and `ER` as in D2.
- **Generation.** The implementation computes all tables at import time with exact
  big-integer arithmetic (at least 64 guard bits), not with floating-point
  `sin`, `cos` or `pow`. No table entry is an exact tie, so the result is the
  correctly rounded value. The table digests below are checked by tests.

Per event `j` with `n_j` samples, for `i = 0..n_j - 1`:

```
phase_h = (INC[profile][p_j][h] * i) mod 2^32
s_h     = S[phase_h >> 16]                        # 16-bit index, no interpolation
mix     = 20 * s_1 + 3 * s_2 + 1 * s_3            # weights 1, 0.15, 0.05 times 20
e       = mix * k_j * env(i)                      # k_j from D5
x       = floor((e + 2^30) / 2^31)                # round half up to the working scale
```

Gaps are `x = 0`. All intermediate values fit in a signed 64-bit integer
(`|e| < 2^53`).

Table digests (SHA-256 of the little-endian bytes):

| Table | Encoding | SHA-256 |
| --- | --- | --- |
| `S` (65,536) | int32 | `6e699ea4ff420efc9136bea3ef416606b851675d0873e94028e6fe5902ad28c8` |
| `EA` (481) | int32 | `d311e617fcd1c3e452b8677a5216af3d0c31e634050dd1b76eb8cb7d4f5626cc` |
| `ER` (1,441) | int32 | `2510eea224e7f75712c80f29b7aecf6b2e795360451067448c079416ea410708` |
| `INC` (117, order P1..P3, p −6..+6, h 1..3) | uint32 | `14864688cdbb9cacbd6f633485b15c902a7416f0e38a2b8c2616c5b809bdd5f0` |

Rationale: identical bytes on macOS, Linux and Windows are a requirement (Study A
protocol §3.2: hash the stored waveform). Integer arithmetic makes that
true by construction instead of by luck. With a 65,536-entry table the
phase-truncation spurs are about 96 dB below the carrier, below the 16-bit
quantization floor. Frequency resolution is 48000 / 2^32 ≈ 1.1e-5 Hz.

### D5. Amplitudes

Each amplitude becomes an integer `k = 5 * a`, which is 3, 4 or 5. The three
integers are then divided by their greatest common divisor:
`k_j = k_j / gcd(k_1, k_2, k_3)`.

The divisor is 1 for every triple except the uniform ones. (0.6, 0.6, 0.6),
(0.8, 0.8, 0.8) and (1.0, 1.0, 1.0) all render with `k = (1, 1, 1)`.

Rationale: normalization (D6) removes the overall level. Uniform triples are
therefore the same sound, and with this rule they are also the same bytes. The
duplicate check (`E_DUPLICATE`) then catches them. Without the rule they would
differ by rounding, and they would also pass the separation screen: their
amplitude features differ by 0.5 each, giving a distance of 0.25. No other two
triples in the domain are proportional, so the rule changes nothing else.
Amplitude ratios within a motif are preserved exactly.

### D6. Normalization

Each motif is normalized to one fixed RMS target over its full length, including
the gaps:

```
N = T * 48
S = sum(x^2)                                     # exact integer
G = isqrt((RMS_TARGET^2 * N * 2^64) // S)        # gain, Q32
y = floor((x * G + 2^31) / 2^32)                 # output samples
```

`RMS_TARGET = 7336` LSB, which is −13.00 dB relative to full-scale code 32,767.

**Headroom.** The worst-case crest factor (peak / RMS) was measured in two stages:

1. All 2,097 admissible timing structures times 27 amplitude triples, at pitch
   (0, 0, 0), profile P1.
2. The 15 worst structures from stage 1 times all 2,197 pitch triples times all 3
   profiles.

The worst crest factor is 8.814 dB (T=450, weights 4/4/2, gaps 60/60,
amplitudes 0.6/0.6/1.0). Pitch and profile change it by less than 0.01 dB.
Worst-case peak is therefore −4.19 dBFS: **4.19 dB of headroom**, above the
3 dB minimum. The continuous waveform `sin t + 0.15 sin 2t + 0.05 sin 3t` peaks
at 1.0113, so no sample can exceed the bound by more than its sampling error.

This is digital level only. It is not a sound-pressure calibration (Common
procedures §2). Individual playback gain is set at calibration (Common
procedures §4) and normalization does not replace it.

Rationale: RMS normalization keeps loudness comparable across motifs with
different duty cycles, so level is not an uncontrolled cue. One target for
every motif keeps it a property of the renderer, not of any method.

### D7. Reject, never limit

There is no limiter, soft clip or second normalization pass. If any output sample
has `|y| > 32767` (−32,768 is also treated as overflow), the renderer sets the
`overflow` flag and produces no PCM bytes. The validator rejects the recipe with
`E_CLIP`. With D6 this cannot happen inside the recipe domain. The check stays,
because the protocol requires it and because it protects against a future change
of target.

The renderer never returns non-finite values, because it uses integers. It still
reports a `nonfinite` flag (always false) so the validator's `E_NONFINITE` check
has a defined input.

### D8. Bit depth and WAV format

16-bit signed PCM, little endian, mono, 48,000 Hz. Each file is a canonical
44-byte header followed by the samples. There are no other chunks, no metadata
and no timestamps.

| Offset | Size | Value |
| --- | --- | --- |
| 0 | 4 | `RIFF` |
| 4 | 4 | `36 + 2 * n_samples` (uint32 LE) |
| 8 | 4 | `WAVE` |
| 12 | 4 | `fmt ` |
| 16 | 4 | 16 |
| 20 | 2 | 1 (PCM) |
| 22 | 2 | 1 (channels) |
| 24 | 4 | 48000 |
| 28 | 4 | 96000 (byte rate) |
| 32 | 2 | 2 (block align) |
| 34 | 2 | 16 (bits per sample) |
| 36 | 4 | `data` |
| 40 | 4 | `2 * n_samples` |
| 44 | ... | samples, int16 LE |

Rationale: 16-bit PCM with a minimal header is the most widely supported format
and gives about 88 dB of signal-to-noise ratio at the RMS target (quantization noise
is about 0.29 LSB RMS), which is enough for comfortable listening levels. Unity imports it without a decoder. The Unity app must keep the
clip as PCM (no Vorbis or ADPCM recompression, no sample-rate override). It must
also verify the SHA-256 of the raw file bytes before decoding. **Pending:**
confirmation from the audio-subsystem owner (#64) that this loads byte-exact on
Quest Pro.

### D9. What is hashed

- `pcm_sha256`: SHA-256 of the sample bytes only (the `data` chunk payload,
  int16 LE). This identifies the waveform and is used for duplicates, reserved
  signals and the vocabulary store.
- `file_sha256`: SHA-256 of the complete canonical WAV file. Because the header is
  a function of `n_samples`, it adds no information. It lets a loader check a
  file without parsing it.
- Message composite hash: SHA-256 of `pcm(action) + 9,600 zero samples (19,200
  zero bytes) + pcm(referent)`, computed in memory (#10, `composite_hash`).
- Hex digests are lowercase. Hash files are written with `\n` line endings and are
  never subject to line-ending conversion (`.gitattributes`).

### D10. Renderer version and renderer hash

- `RENDERER_VERSION = "0.1.0"` (pilot). It becomes `1.0.0` at the G4 freeze.
  Any change to rendered bytes for any valid recipe increments the version
  (minor before G4, major after G4) and regenerates the golden hashes in the same
  pull request. Every hash record (store, golden manifest, package) stores the
  renderer version.
- `renderer_hash` is the SHA-256 of the compact canonical JSON
  (`sort_keys`, separators `,` and `:`) of:
  - `renderer_version`
  - every numeric constant: sample rate, table sizes, Q formats, attack, release,
    harmonic weights, profile `f0`, `RMS_TARGET`, full-scale code
  - the four table digests
  - the SHA-256 of each renderer source module, with CRLF normalized to LF
- `renderer_recipe_schema_hash` is the SHA-256 of the compact canonical JSON
  `{"recipe_schema_sha256": ..., "renderer_hash": ...}`. The schema digest covers
  the schema file bytes, with CRLF normalized to LF. This value goes into the
  apparatus manifest field `renderer_recipe_schema_hash` and the G4 freeze list.

### D11. Checks a JSON schema cannot express

The schema enforces field names, types, array lengths and allowed values. These
checks belong to the validator (#9), each with a reason code:

| Check | Code |
| --- | --- |
| Any event shorter than 2,880 samples (D1) | `E_EVENT_SHORT` |
| Non-finite samples | `E_NONFINITE` |
| Overflow after normalization (D7) | `E_CLIP` |
| `pcm_sha256` equal to a committed entry | `E_DUPLICATE` |
| Collision with a reserved signal (`sound/reserved/registry.json`) | `E_RESERVED` |
| 12-feature distance below the threshold to a committed motif | `E_SEPARATION` |

The validator also rejects integer fields given as JSON numbers with a fraction,
such as `450.0`.

## 4. Recipe format

The recipe is a JSON object with exactly five fields. The profile is not part of
the recipe; it is passed to `render()` separately.

```json
{"amplitudes":[1.0,0.6,0.8],"gaps_ms":[40,20],"pitches":[-3,0,4],"rhythm_weights":[2,1,3],"total_ms":600}
```

The canonical form, used for hashing and storage, is compact JSON with sorted keys,
integers without fraction, and amplitudes written as `0.6`, `0.8` or `1.0`.
Every field in [`recipe.schema.json`](../schema/recipe.schema.json) is an
enum, so the schema can go to schema-constrained decoding (#16, #17) without
changes.

## 6. Known limitation (flag for the threshold review)

The separation features include absolute amplitudes, but D6 removes overall level.
Two non-uniform triples, such as (0.6, 0.8, 0.8) and (0.8, 1.0, 1.0), have
different features (distance contribution 0.5 per event) but nearly equal ratios
(0.75 versus 0.8). D5 removes the exact case (uniform triples). The near-equal
cases remain for the separation-threshold listening check (O6.2.2) to judge.
