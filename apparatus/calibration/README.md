# Audio onset calibration records (#80)

This directory holds audio onset calibration records for the route chosen in
ADR-005. Each record covers one station, one route and one set of device settings.
It is the target of the apparatus manifest field `audio_onset_calibration_record`.

**There are no records here yet.** No physical measurement has been made. The
analysis tool and schemas exist, but no route, buffer or station is calibrated
or qualified.

## Where a record comes from

A real record comes only from a physical measurement on station hardware. Stored
48 kHz mono stimuli are played through the app's scheduled playback path with the
full scene loaded. Output is captured at the coupler, plus a loopback reference
where available. The operator then runs `tools/onset_calibration.py analyze` on
that capture. The procedure is in
[the O6.1.3 runbook](../../docs/spikes/O6.1.3-runbook.md).

Synthetic examples are test fixtures, never calibration evidence:

- `apparatus/examples/audio-onset-calibration-settings.example.json`
- `apparatus/examples/audio-onset-calibration.example.json`

They carry `evidence_kind: synthetic_fixture`, and the schema keeps them
`provisional`. The example record is regenerated byte for byte by
`tests/test_onset_calibration.py` from a generated WAV. Do not copy its numbers
into station configuration, and do not put synthetic records in this directory.

## Layout

One directory per measurement run:

```text
apparatus/calibration/<station_id>/<route>/<YYYYMMDD>-<capture_kind>-<play_mode>/
  audio-onset-calibration.json   # record (schema: apparatus/schemas/audio-onset-calibration.schema.json)
  plays.csv                      # per-play status, onset, offset and residual
  residual-histogram.csv         # 1 ms residual bins
  settings.json                  # the exact settings file that was analysed
  events.csv, sync-anchors.csv   # the exact analysed inputs
```

The record pins the SHA-256 of the capture WAV, the events CSV, the sync CSV and
the settings, and of both output CSVs. Raw capture WAVs are binary. Commit them
only as Git LFS objects (`.gitattributes` already routes `*.wav` to LFS), or keep
them in the lab's private evidence store and rely on the pinned hash. Captures
of the public test stimuli contain no participant data. Never commit participant
recordings or `*.local.*` files here.

Run `python tools/onset_calibration.py check <run-directory>` to revalidate a
stored record against its schema and its output hashes.

## Status and invalidation

- The tool only writes `status: provisional`.
- A record may be changed to `qualified` only by a reviewer. The schema then
  requires all of the following:
  - `evidence_kind: physical_measurement`
  - `capture_kind: acoustic_coupler`
  - `full_scene_loaded: true`
  - `play_mode: scheduled`
  - a `review` block
  - either `target.met: true` or a signed `response_time_qualification`
- A qualified record applies only to its own station, route, connection mode,
  play mode, output device, buffer size and count, sample rate, volume step and
  app build. If any of these change, the record is invalid until the measurement
  is rerun. Keep superseded records; do not edit them in place.
- Every record uses `reference_field: scheduled_onset_mono_ms`; the schemas refuse
  `audio_request_mono_ms`. The app derives `audio_onset_estimate_mono_ms` as
  `scheduled_onset_mono_ms` plus `route_offset_ms`, matching Unity's
  `AudioTiming.Schedule`. It logs `onset_uncertainty_ms` from the current qualified
  record. The Unity loader that reads these records is separate work.
